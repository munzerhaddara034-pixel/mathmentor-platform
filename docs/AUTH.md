# Auth, sessions, and lesson protection

Prof. Munzer Haddara / الأستاذ منذر حداره.

This build uses a **JSON session store** (`auth.json`) — the same adapter as promo cards, HeyGen jobs, live bookings, and notifications. There is still no external IdP.

## Persistence (Netlify Blobs vs local)

`readJsonFile` / `writeJsonFile` in `src/lib/dataDir.ts` pick a backend:

| Runtime | Where `auth.json` (and other JSON stores) live |
| --- | --- |
| **Netlify production** / `netlify dev` / Lambda (`NETLIFY`, `AWS_LAMBDA_FUNCTION_NAME`, …) | **Netlify Blobs**, site-scoped store `mathmentor-data`, key = filename (`auth.json`, `store.json`, …). Strong consistency so a login on one function instance is visible on the next request. |
| Local `next dev` / `next start` | Gitignored `data/` folder on disk. |

A cold start / missing blob starts with an **empty** store (no demo accounts are seeded). Set `NETLIFY_BLOBS_DISABLED=1` only to force the filesystem fallback.

**Do not store sessions in `/tmp`.** `/tmp/mathmentor-data` is per-instance and ephemeral. That was the production bug: login wrote `auth.json` on instance A; the next navigation hit instance B with an empty file; `findSessionByToken` missed; the UI treated it as `/login?reason=replaced`.

Binary uploads (solver images under `public/uploads`) stay on the local disk / `/tmp` and are not Blobs-backed. Voice-to-Math job JSON and recorded audio (`voice-math.json`, `voice-audio-*.json`) use the same Blobs/filesystem JSON helpers.

## What is protected

Unauthenticated visitors to private routes are redirected to `/login` (middleware + server layouts + client fallback).

| Role | Lessons + solver (`/lessons/*`, `/math-solver`, `/studio/player`…) | Live booking (`/live`) | Staff (`/studio/script`, `/studio/voice-solver`, `/admin`, `/professor`…) |
| --- | --- | --- | --- |
| Student / parent with **AI_TIER** or **BOTH** | yes | BOTH only | no |
| Student with **LIVE_TIER** only | no → `/redeem?need=ai` | yes | no |
| Student without plan | `/redeem` | `/subscribe?need=live` | no |
| Teacher / admin | yes | yes | yes |

`?teacher=1` still requires a **logged-in teacher or admin**. Students cannot open the timeline editor.

Private pages send `X-Robots-Tag: noindex, nofollow, noarchive` and `<meta name="robots" content="noindex, nofollow" />`.

## Device sessions (students vs teacher)

Each login issues a new opaque cookie (`mm_session`) and records a device fingerprint (`userAgent + screen + timezone + localStorage deviceId`). Device names shown in the UI are derived from the User-Agent (e.g. `Windows Chrome`, `iPhone Safari`, `Android Chrome`) plus a Desktop/Mobile label. Timestamps use **Asia/Beirut**.

**Students / parents:** the account may keep **one mobile and one desktop** session. A second login of the *same class* deletes the previous session of that class **and records that token hash in `revokedTokens`**. The old cookie is then sent to `/login?reason=replaced` (English + Arabic). One phone **and** one computer may stay signed in together.

**Teacher / admin** (role `teacher` or `admin`): prior sessions are **not** invalidated when signing in from another device. The professor can stay logged in on two or more desktops. Instead, every successful staff login creates an in-app notification «جهاز جديد نشط / New active device» naming that device. Alerts appear in the header bell and on `/dashboard` together with an **أجهزتي النشطة / Active devices** card. Re-login from the *same* browser only replaces that browser’s own ghost session.

`getLiveSession` reasons:

| Cookie | Live session row | `revokedTokens` hit | `reason` | Login copy |
| --- | --- | --- | --- | --- |
| missing | — | — | `unauthenticated` | none (plain sign-in) |
| present | missing | **yes** (student same-class kick) | `replaced` | “signed in on another device” |
| present | missing | **no** (empty store, TTL, logout leftover) | `expired` | “session ended, sign in again” — **not** “another device” |

`replaced` is reserved for an explicit kick. A missing blob or a new function instance must never show the “another device” message.

The cookie is `Secure` only on HTTPS (or `AUTH_COOKIE_SECURE=1`). `npm start` on `http://localhost` still stores the session.

## Accounts and staff rights

The login screen is **logo + title + email/password + Sign in** only. There are **no seeded demo accounts** and no demo promo codes: every account is created on `/signup`, and codes are generated by staff from the teacher console.

- **Signup** (`POST /api/auth/signup`) creates a **student** (or **parent**, if chosen in the form). The password is checked **server-side**: at least 10 characters with at least one letter and one digit (`src/lib/auth/passwordPolicy.ts`), with an Arabic error message.
- **`ADMIN_EMAILS`** (comma-separated, case-insensitive, trimmed): an email on this list gets the **admin** role (staff: teacher + admin powers) when it signs up, and is (re)granted admin on login if the account already exists. Accounts not on the list are never changed. If `ADMIN_EMAILS` is unset or blank, the documented fallback value is `munzerhaddara2@gmail.com` (an allowlist value only — never a stored account or password). Code: `src/lib/auth/adminAllowlist.ts`.
- **`TEAM_APPROVER_EMAILS`** (same format): who may click «موافقة ونشر» in `/admin/team`. Falls back to the `ADMIN_EMAILS` list when unset.
- **Email ownership is not verified at signup.** Until the owner registers each allowlisted address, whoever signs up first with it would receive admin rights. Register the admin email right after deploying.

### Removal of the old demo accounts

`src/lib/auth/removeDemoAccounts.ts` runs once at startup (`src/instrumentation-node.ts`). It deletes only these ten hardcoded seed emails — never by pattern, role or domain:
`student@mathmentor.local`, `pending@mathmentor.local`, `parent@mathmentor.local`, `ai@mathmentor.local`, `live@mathmentor.local`, `teacher@mathmentor.local`, `admin@mathmentor.local`, `student@mathmentor.lb`, `teacher@mathmentor.lb`, `parent@mathmentor.lb`.

For the matched user ids it also deletes their sessions and revoked-token markers (`auth.json`), profile rows (enrollments, lesson progress, exam reminders), notifications, gamification profiles, billing ledger rows and store entitlements — in the active JSON backend (Postgres `mm_documents`, Netlify Blobs or `data/*.json`, plus any local `data/*.json` import source), the Postgres profile tables and the SQLite `data/auth.db` (when that file exists). Each store records that it ran (`data-migrations.json`, `mm_schema_migrations` id `data_001_remove_demo_accounts`, SQLite `mm_data_migrations`), so later boots are a no-op. The log line reports row counts only. Test: `npx tsx scripts/test-demo-account-cleanup.ts`.

## How to verify

**Adapter + kick markers (no browser)**

```bash
npx tsx scripts/verify-auth-persistence.ts
```

This checks: shared-backend `auth.json` survives a simulated second instance; cookie + missing row without `revokedTokens` is `expired` not `replaced`; student same-class login records a real replacement; teacher second desktop is not kicked.

**Local app**

1. `npm run dev`. Sign up / sign in with an email listed in `ADMIN_EMAILS` (staff).
2. Open `/dashboard`, then `/lessons/interactive`, then `/studio/script`. You must **not** land on `/login?reason=replaced`.
3. Student kick: sign in with a student account (created on `/signup`) on two desktop profiles. The first session should redirect to `/login?reason=replaced` on the next navigation.

**Netlify production**

1. Deploy this branch. In the Netlify UI, Blobs → store `mathmentor-data` should gain key `auth.json` after the first login.
2. Sign in as Prof. Munzer Haddara (an `ADMIN_EMAILS` account). Click dashboard, lessons, and studio. Function logs may show different instance IDs; the session cookie must still work (no `reason=replaced`).
3. Repeat the student same-class kick from two browsers. That path still sets `replaced` because the kicked token hash is stored in `revokedTokens` on the shared blob.

## Merge note (agent-hub-latest): one session authority

`agent-hub-latest` merges the Render branch (`cursor/platform-shell-auth-dashboard-2f19`, SQLite
role dashboard + signed-cookie sessions) with this Agent Hub codebase. There is now **one** session
mechanism: the opaque, server-side exclusive session in `src/lib/auth/session.ts` (`mm_session`).

- `src/lib/auth/server.ts` keeps the Render API (`getSession`, `getFreshSession`, `requireSession`,
  `requireRole`) as an adapter over `getLiveSession()`, enriched with the SQLite profile in
  `src/lib/auth/db.ts` (linked student, track, enrollments) matched by email. `admin` maps to the
  dashboard role `teacher`.
- `POST /api/auth/login` checks the session store first, then the SQLite profile DB; a matching
  SQLite account is mirrored into the session store (`ensureUserForProfile`).
- `POST /api/auth/signup` writes the SQLite profile **and** the session-store user, then starts an
  exclusive session. Self-signup is limited to `student` / `parent`; staff accounts are provisioned.
- The old HMAC signed-cookie format is retired, so users signed in on Render before the merge sign
  in once more. `AUTH_SECRET` is no longer read.
- `/dashboard` is open to every signed-in role: students/parents get the SQLite role dashboard,
  staff get the teacher console (`TeacherOpsPanel`: codes, top-ups, devices, Agent Hub links).
