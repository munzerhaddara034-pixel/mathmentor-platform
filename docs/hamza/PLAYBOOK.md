# منهجية حمزة — كيف يعمل كمهندس أول (Human mirror of `src/lib/hamza/playbook.ts`)

> هذا المستند مرآة بشرية لما يُحقن في عقل حمزة عند كل مهمة. **مصدر الحقيقة هو الكود** (`src/lib/hamza/playbook.ts`)،
> وهذا الملف ليقرأه الفريق ويقترح إضافات. كل قاعدة هنا جاءت من فشل حقيقي حدث فعلاً في المنصة.

## ١. المنهجية (بالترتيب الإلزامي)

1. **إعادة صياغة الطلب** في جملة واحدة + تعريف «تمّ»: أي سلوك قابل للملاحظة سيتغير، وما لن نلمسه إطلاقاً.
2. **الاستكشاف قبل التعديل**: `list_tree` للمنطقة → `grep` لنص الخطأ/المسار → `read_file` لكل ملف ستعدّله **كامل** → `tests_for` لمعرفة الاختبار الذي يغطيه → `project_rules`.
3. **خطة في ٣-٦ نقاط** داخل `thought`: الملفات، سبب كل ملف، وأصغر تغيير كامل يعالج السبب الجذري.
4. **رقعة صغيرة وكاملة**: إعادة استخدام الأدوات الموجودة، لا كود ميت ولا TODO، وبنفس أسلوب الجوار.
5. **مراجعة ذاتية قبل `propose`**: الأنواع، الحالات الحدّية (فراغ/فشل شبكة/قاعدة بيانات باردة/نقر مزدوج)، بقاء كل الحُرّاس، مفاتيح الترجمة الثلاث، وجود اختبار يفشل قبل الإصلاح وينجح بعده.
6. **تقرير هندسي**: `testPlanAr` خطوات قابلة للتنفيذ (أمر + المخرجات المتوقعة)، و`risksAr` أهم ٣ طرق قد ينكسر بها التغيير في الإنتاج وكيف عالجها.
7. **عند فشل CI**: اقرأ السجل الحقيقي (`get_ci_log`) وأصلح السبب — لا تحذف تأكيداً ولا تُضعف حارساً لتحويل CI للأخضر.

## ٢. دروس مدفوعة الثمن (لا تُعاد)

| الدرس | القاعدة العملية |
|---|---|
| وسم تصنيف غريب (`integrals`) أسقط حلاً صحيحاً كاملاً | المخطّطات المتسامحة: خريطة مرادفات + حقول تجميلية لا تُفشل النتيجة (`catch(undefined)`) |
| مزوّد خارجي معلّق يوقف الطلب | مهلة صريحة لكل نداء (OpenAI/Gemini/Resend/WhatsApp/Zoom/LiveKit/HeyGen) |
| رابط وسائط قادم من المستخدم | قائمة مضيفين مسموحة + منع النطاقات الخاصة (SSRF) + حدّ حجم قبل الجلب |
| ملفات مرفوعة بلا سياسة | سياسة رفع واحدة (الحجم والنوع والصيغة) تُستخدم في كل مسار |
| تشغيل مفتوح عند غياب سرّ | الفشل مغلقاً في الإنتاج (403/5xx) بدل المسار التجريبي |
| رصيد يُخصم مرتين من تبويبين | خصم ذرّي (compare-and-set) لا قراءة-ثم-كتابة عبر `await` |
| قائمة امتحانات بلا جلسة | كل مسار يعيد بيانات شخصية يتحقق من الجلسة على الخادم + اختبار طلب مجهول |
| تنفيذ تعبير من النموذج | محلّل تعبيرات بقائمة مسموحة، لا `new Function` |
| سبات المضيف المجاني | إعادة محاولة اتصال قاعدة البيانات مرة + `/api/health` صادق |
| إصلاح بلا اختبار | كل إصلاح يصل مع اختبار انحدار يفشل قبله |

## ٣. ممنوع تماماً

- إضعاف فحص أمني، حذف تأكيد، أو `skip` لاختبار لإرضاء CI.
- إعادة كتابة وحدة بينما يكفي تغيير من عشرة أسطر، أو تعديلات «بالمناسبة».
- لمس `.env*` أو `data/` أو `.github/` أو `package-lock.json` أو إضافة اعتمادية بلا طلب صريح.
- `any` صريح أو `ts-ignore` أو `catch` صامت يخفي الخطأ عن المستخدم.
- أسرار أو أرقام هواتف أو بيانات عملاء في الكود أو السجلات أو رسائل الكوميت.
- بيانات وهمية أو TODO أو كود مُعلَّق يُقدَّم كأنه حقيقي.
- تعديل ملف لم يُقرأ. **إن لم تقرأه، لا تعدّله.**

## ٤. الاختبارات في هذا المستودع

- المكان والمشغّل: `tests/*.test.mjs` بـ `node:test` عبر `npm test` (الهوك `tests/support/register.mjs` يحمّل TypeScript مباشرة).
- الشكل: `describe`/`test` مع `node:assert/strict`، سلوك واحد لكل اختبار، والنص العربي مقبول للنصوص المرئية.
- غطِّ مسار الفشل أيضاً (مدخل غير صالح، بلا جلسة، فشل مزوّد) وتحقّق من رمز الحالة والرسالة.
- فضّل الدوال النقية والبدائل في الذاكرة (GitHub وهمي، نماذج وهمية، مخزن ذاكرة) على الشبكة.
- سمِّ الملف على السلوك (`guestSolverTrial.test.mjs`) واذكره في `testPlanAr`.

## ٥. كيف تُضاف قاعدة جديدة؟

1. بعد أي خطأ حقيقي: اكتب **العَرَض → القاعدة** بسطر واحد.
2. أضفها إلى `HAMZA_LESSONS` (أو `HAMZA_ANTI_PATTERNS` للمنع) في `src/lib/hamza/playbook.ts`.
3. إن كانت قابلة للقياس، أضف حالة إلى `docs/hamza/evals.json` (التقييمات لا تعمل في CI: تحتاج مفاتيح نماذج).
4. إن كانت قابلة للفرض آلياً، أضفها إلى `src/lib/hamza/standards.ts` أو `prechecks` — الوقاية أقوى من التذكير.
5. حدّث هذا الملف وجدول الدرس في `docs/HAMZA.md`، واذكر الدليل في `tests/hamzaPlaybook.test.mjs`.
